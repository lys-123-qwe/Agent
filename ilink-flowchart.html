📌 扫码登录原理
请求微信 iLink 服务器获取二维码 → 服务器返回 qrcode_id 和二维码图片 URL → 打印到控制台供用户扫码 → 每 2 秒轮询二维码状态 → 用户扫码确认后返回 bot_token（身份凭证）和 baseUrl（可能变化，用于负载均衡）。

★ 关键：bot_token 是后续所有请求的密码， baseUrl 可能从 ilinkai 变为 ilinkii，需要动态重建 RestClient。

📌 长轮询消息拉取
登录成功后启动独立线程，每 3 秒发起一次 getUpdates 请求。 这是长轮询（Long Polling）：服务器挂起连接最多 35 秒， 有消息到达立即返回，无消息则超时空返回。

每次返回 get_updates_buf（游标），下次请求时带回， 确保不重复消费消息 → 用 cursor 变量维护。 收到消息后提取文本和 contextToken，进入路由处理。

📌 DeepSeek AI 对话机制
每个微信用户独立对话 session，存储为 ConcurrentHashMap<String, List<ChatMessage>>。 session 结构：[system消息, user消息, assistant回复, user消息, ...]。

最多保留 10 轮对话，超出后删除最早的历史（保留 system 消息）， 这是 trimHistory() 方法的作用。

★ HTTP 请求同样使用 byte[] 编解码，防止 Windows 乱码。

📌 发送回复的关键细节
client_id： 每次发送必须使用不同的 UUID，微信用来去重（幂等性）。
context_token： 必须原值带回接收消息时的 token，用于关联原消息。
X-WECHAT-UIN： 每次请求生成新的随机数，防重放攻击。 生成逻辑：随机整数 → 无符号十进制字符串 → Base64 编码。
byte[]： Windows 默认 GBK 编码，body(String.class) 会乱码。用 byte[] 拿到原始字节再 UTF-8 解码。

★ 响应 {} 仅表示服务器接受，不代表消息已送达用户微信。

📌 断开清理
polling.set(false) 使轮询循环条件不满足 → 线程自然退出。 connected.set(false) 标记连接断开。 调用 pollThread.interrupt() 中断可能的 sleep 等待。 最后清除 bot_token 使认证失效。

★ 线程标记为 daemon，即使忘记调用 stop，程序退出时也会自动结束。
